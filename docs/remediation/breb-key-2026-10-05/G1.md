## M1 — Configuración, render y publicación

Los cuatro campos bancarios existentes tienen prefijo BOOKING_*:
BOOKING_BANK_NAME, BOOKING_ACCOUNT_TYPE, BOOKING_ACCOUNT_NUMBER,
BOOKING_ACCOUNT_HOLDER. Están en app/config/settings.py:111–114 y
.env.example:50–53; su valor por defecto es vacío. Settings valida secretos de
producción en :165, pero no valida estos datos al arrancar. El guard bancario
está en app/orchestrator/booking_flow.py:573–585, antes de crear la solicitud de
pago. El handler pasa Settings como valor de bank_name/account_type/
account_number/account_holder en :665–671, junto a deposit_amount.
app/conversation/presentation.py:138 solo acepta Settings para datos bancarios;
los presenters se registran en :297–301. La llave seguirá ese mismo contrato.

La única plantilla de instrucciones con variables bancarias es
RESP-BOOKING-PAYMENT-001: docs/conversation/approved-responses.md:2890.
Está documentada APPROVED, aprobada por Leandro el 2026-10-02, versión productiva
v2. allowed_variables son account_holder, account_number, account_type,
bank_name y deposit_amount. Se enviará una nueva versión con breb_key, sin
cambiar ninguna palabra del texto anterior. La línea propuesta para aprobación
es exactamente «Llave Bre-B: {breb_key}».

El seed extrae el texto y sus variables desde approved-responses.md
(data/knowledge_seed.py:47–74). Hasta este cambio, KnowledgeSeedEntry usa v1
por defecto para todos los códigos (:42), incluso cuando docs menciona una
versión productiva v2. Por eso editar únicamente la copia no publica una
identidad nueva con el loader de deploy. Se declarará v3 solo para PAYMENT.

scripts/load_knowledge.py:24–47 usa identidad código+versión, conserva filas
existentes y marca INACTIVE las versiones anteriores al insertar una versión
nueva. deploy.sh:20 ejecuta ese loader después de Alembic y antes de arrancar
app/worker. scripts/sync_knowledge_versions.py:48–88 compara texto, resumen,
categoría y allowed_variables; CREATE usa actualmente v1 y BUMP max+1.
Debe respetar el mínimo explícito del seed para publicar v3 desde v1 o v2;
con una versión posterior, sigue incrementando. Su CLI ya prohíbe production
(:165); este bloqueo se conserva. No se ejecutará publicación de producción.

app/conversation/knowledge.py:53–83 renderiza exclusivamente la última versión;
si no está APPROVED no revive una anterior. Las variables deben estar en
allowed_variables; una variable adicional falla con KnowledgeRenderError /
UNKNOWN_VARIABLE. La validación de arranque debe usar esa misma selección y
consultar si el texto contiene breb_key, porque la versión anterior no lo usa.
API crea el sessionmaker en app/main.py:21–32; worker lo hace en
app/channel/worker.py:636–646. Ambas entradas deben validar antes de empezar a
atender, cerrando el engine aun cuando falle la validación.

Conclusión de publicación: seed + sync son suficientes; no hay migración,
nuevo estado, nuevo pending_action ni un código de plantilla nuevo.
